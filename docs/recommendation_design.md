# 위치 추천 알고리즘 설계안 (v0.1)

> 상태: **설계 초안 - 구현 전 확인용**. 가상 데이터로 검증한 결과는 "설계 의도를 구분하는 능력"이지 실제 현장 성능이 아니다.

---

## 1. 문제 정의

**입력**

- `trap_day_summary` (트랩 × 위치 × 날짜 일 집계) — 실제 또는 가상
- 트랩 위치 이력, 위치 목록(후보 위치 포함), 분석 기간

**출력** (트랩별, 분석 기간 끝 시점에 설치 중인 트랩만)

- 판단 `status`: `keep` / `recommended`(재배치 권고) / `insufficient_data` / `device_check`(장치 점검)
- 추천 위치, 점수, 우선순위, 사유(근거 문장), 통계

**풀어야 하는 질문**

1. 이 트랩의 현재 위치는 성과가 좋은가?
2. 성과가 낮다면 원인이 **위치**인가 **장치**인가? (장치 문제면 옮겨도 소용없음)
3. 위치 문제라면 어디로 옮길 것인가?
4. 데이터가 부족한 경우는 판단을 보류한다.

## 2. 접근 방식: 규칙 + 점수 기반 (머신러닝 미사용)

- 포획 데이터가 가상이고 표본이 작아(트랩-일 129행, 위치 5곳) 머신러닝은 검증 불가능하고, 가상 데이터의 생성 규칙을 학습하는 순환 검증이 된다.
- 규칙·점수 기반은 판단 근거를 문장으로 설명할 수 있어 대시보드에 "추천 사유"로 그대로 쓸 수 있다.
- 실제 데이터가 충분히 쌓이면 다시 검토한다.

## 3. 알고리즘 단계

### 3-1. 기본 통계 (트랩×위치 / 위치 단위)

`metrics.aggregate_performance` 결과를 사용: `observed_days`, `operating_hours`, `rat_detections`, `detection_rate`, `sim_captures`, `sim_conversion`.

### 3-2. 전환율의 불확실성: Wilson 신뢰구간

전환율은 `포획 / 감지`라 감지 건수가 적으면 흔들린다(EDA: LOC-C 35건 → 17.1%, 6/35). 점 추정값 대신 **Wilson 95% 구간 [lb, ub]** 로 비교한다.

- "낮다" 판정은 구간이 **겹치지 않을 때만** 내린다 (예: 낮은 쪽 `ub` < 높은 쪽 `lb`).
- 표본이 적으면 구간이 넓어져 자연스럽게 판단이 보류된다.

### 3-3. 데이터 충분성 (판단 보류 조건)

다음 중 하나면 해당 트랩은 `insufficient_data`로 두고 추천을 확정하지 않는다.

- 현재 위치 관측 일수 < 7일 또는 작동 시간 < 72시간
- 쥐 감지 건수 < 10건 (전환율 구간이 지나치게 넓음)

### 3-4. 원인 분리: 위치 문제 vs 장치 문제 (감지는 있는데 전환율이 낮은 트랩)

"낮음" = 해당 트랩×위치의 전환율 `ub` 가 기준 비교 대상의 `lb` 보다 작음.

| 증거                                                        | 판단                                                                               |
| ----------------------------------------------------------- | ---------------------------------------------------------------------------------- |
| 같은 위치·같은 기간의 **다른 트랩은 높은데** 이 트랩만 낮다 | **장치 의심**                                                                      |
| 이 트랩이 **다른 위치에서도 낮았다**(이동 이력)             | **장치 의심**                                                                      |
| 이 트랩이 **다른 위치에서는 높았다**                        | 장치 정상 → **위치 문제**                                                          |
| 같은 위치의 다른 트랩도 낮다                                | **위치 문제**                                                                      |
| 위 증거가 모두 없음 (트랩 1대, 이동 이력 없음)              | **원인 미확정** — 위치 문제 가능성으로 재배치를 제안하되 사유에 "원인 미확정" 표기 |

장치 의심 트랩은 `device_check`로 표시하고 재배치를 권고하지 않는다. 또한 이 트랩의 데이터는 **위치 점수 계산에서 제외**한다(EDA에서 LOC-A 전환율이 고장 트랩 때문에 낮아 보이는 문제 확인).

### 3-5. 위치 점수

장치 의심 트랩을 제외한 데이터로 위치별로 합산한 뒤:

```
위치 기대 포획률 = detection_rate × conversion_lb      (conversion_lb: Wilson 95% 하한)
위치 점수(0~1)   = 위치 기대 포획률 / (평가 가능한 위치 중 최댓값)
```

- `detection_rate × conversion`은 "작동 1시간당 기대 가상 포획 수"로 해석이 쉽고, 감지만 많거나 전환만 높은 위치가 과대평가되지 않는다.
- 하한(보수적 추정)을 써서 표본이 작은 위치가 우연히 높게 나오는 것을 막는다.
- 점수는 **현재 관측된 위치들 사이의 상대값**이다. 절대적인 포획 성능을 뜻하지 않는다.
- 평가 가능 위치: 데이터 충분(3-3) + 장치 의심 트랩 제외 후에도 데이터가 남는 위치. 그렇지 않으면 점수를 `null`로 둔다.

### 3-6. 재배치 결정

트랩이 `insufficient_data`나 `device_check`가 아닐 때:

1. 목표 위치 = 점수가 가장 높은 평가 가능 위치(현재 위치 제외, **설치 이력이 있는 위치만**)
2. **재배치 권고** 조건: `현재 위치 점수 ≤ 0.5 × 목표 위치 점수` **그리고** 목표 위치 점수가 현재보다 구간 기준으로도 의미 있게 높음
3. 아니면 `keep`

우선순위 = `(목표 점수 − 현재 점수)`가 큰 순서(1이 가장 급함).

### 3-7. 설치 이력이 없는 후보 위치 (예: LOC-E)

- 관측값이 없으므로 성과를 예측하지 않는다. v1에서는 **추천하지 않는다** (`recommended_location_type`은 항상 `existing`).
- 후보 위치는 결과의 참고 정보(미검증 후보)로만 둔다. 시험 설치 제안은 이후 단계에서 별도로 논의한다.

## 4. 출력 형식 (API 명세 v1.0 + 변경 1건)

기본은 API 명세 3-1의 구조 그대로 사용한다.

- `status`에 새 값 **`device_check`** 추가 (명세 **v1.1**). 이 경우 `relocate=false`, `recommended_location_id=null`.
- 근거 문장 예: "TRAP-06은 LOC-A·LOC-F 모두에서 감지 대비 가상 포획 전환율이 낮고(3%, 7%), 같은 LOC-A의 다른 트랩은 36% → 위치가 아닌 장치 점검 필요"
- 가상 포획 기반이므로 `data_basis.is_simulation_based = true` 와 시뮬레이션 문구를 항상 포함한다.

> Pi 담당자 확인 필요: `status` 값 한 종류 추가. 문자열로 저장만 한다면 영향이 작을 것으로 예상.

## 5. 검증 계획 (가상 시나리오, `evaluation.py`)

**정답(분석 기간 끝에 설치 중인 트랩 기준)**

| 트랩      | 현재 위치          | 기대 판단                                     |
| --------- | ------------------ | --------------------------------------------- |
| TRAP-01   | LOC-A              | `keep`                                        |
| TRAP-02   | LOC-A (B에서 이동) | `keep` (장치 정상, 위치가 문제였음)           |
| TRAP-03   | LOC-C              | `recommended` → LOC-A                         |
| TRAP-04   | LOC-D              | `insufficient_data`                           |
| TRAP-06   | LOC-A (F에서 이동) | `device_check`                                |
| (TRAP-05) | 기간 중 철수       | 평가 대상 아님, LOC-B 위치 점수 근거로만 사용 |

**검증 방법**

1. 기본 시드(42)로 위 정답과 일치하는지 확인
2. **시드 20개**로 반복 실행해 정답 일치율을 구한다 (한 번 우연히 맞은 것이 아님을 확인)
3. 점수 순서가 설계와 맞는지(LOC-A > LOC-B, LOC-C), LOC-D·LOC-E 점수 `null`
4. 민감도: 임계값(0.5, 10건 등)을 바꿨을 때 결과가 얼마나 변하는지

**보고 원칙:** 가상 데이터 정확도는 "설계된 상황을 구분하는 능력"으로만 보고하며, 실제 현장 성능으로 말하지 않는다. 알고리즘이 생성 모델(포아송·이항)을 가정하지 않도록 Wilson 구간과 상대 비교만 사용한다.

## 6. 한계

- 위치별 수용 가능한 트랩 수를 모른다. 여러 트랩이 같은 최고 점수 위치로 몰릴 수 있다(제한 없음).
- 전환율은 가상 포획이므로 실제 포획 성능과 무관할 수 있다.
- 한 번 옮긴 이력이 있는 트랩에만 원인 분리가 확실하다. 이력 없는 트랩은 "원인 미확정"이다.
- 환경 변수는 가상 데이터로 영향을 검증할 수 없어 점수에서 제외했다.
- 임계값(7일, 72시간, 10건, 50%)은 초기값이며 실제 데이터 확보 후 재조정한다.
- 후보 위치(설치 이력 없음)의 성과는 예측하지 않는다.

## 7. 확인이 필요한 결정

1. **점수 정의**: `감지 빈도 × 전환율 하한`을 최고 위치 대비 0~1로 정규화
2. **재배치 기준**: 현재 점수 ≤ 목표 점수의 50%, 데이터 충분 기준 감지 10건 이상
3. **`device_check` 상태 추가**(API 명세 v1.1, Pi 담당자 확인 필요)
4. **LOC-E 같은 후보 위치는 v1에서 추천하지 않음**
