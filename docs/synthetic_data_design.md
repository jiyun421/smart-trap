# 가상 포획 데이터셋 설계안 및 데이터 사전 (v0.1)

> 상태: **설계 초안 - 구현 전 확인용**. 이 문서에 적힌 모든 "포획" 수치는 **시뮬레이션 값**이며 실제 포획 실적이 아니다.

---

## 1. 목적과 용도

실제 포획 기록이 없으므로 포획 관련 지표는 가상으로 만든다. 용도는 두 가지이며 **서로 다른 데이터셋**으로 분리한다.

| 구분   | 이름                  | 감지 데이터      | 포획 데이터 | 용도                                                               |
| ------ | --------------------- | ---------------- | ----------- | ------------------------------------------------------------------ |
| 모드 1 | **시나리오 데이터셋** | 가상             | 가상        | 알고리즘이 위치 유형(A/B/C/D 등)을 제대로 구분하는지 **검증**      |
| 모드 2 | **결합 데이터셋**     | **실제**(Pi API) | 가상        | 실제 감지 데이터 위에 가상 포획을 얹어 추천 실행·**대시보드 시연** |

- 모드 1은 정답(각 위치의 진짜 특성)을 우리가 알고 있으므로 알고리즘 검증이 가능하다.
- 모드 2는 정답이 없다. 알고리즘 검증용으로 쓰지 않고, 파이프라인이 실제 데이터로 끝까지 도는지 확인하는 용도다.
- 두 모드 모두 **같은 컬럼 구조**를 쓴다(아래 데이터 사전). 구분은 `detection_source` 컬럼으로 한다.

## 2. 분석 단위와 결합 기준

### 2-1. 분석 단위: 트랩 × 위치 × 날짜

API 이벤트(감지, 센서, 상태 로그)를 **하루 단위로 집계**한 표(`trap_day_summary`)를 기본 분석 단위로 한다.

- 트랩이 위치를 옮기면 같은 `trap_id`라도 날짜에 따라 `location_id`가 달라진다. `trap-location-history`로 날짜별 위치를 결정한다.
- 위치별 성과는 `location_id` 기준으로 날짜 행을 합산해 계산한다.

### 2-2. 결합 키

| 결합 대상             | 키                               | 설명                     |
| --------------------- | -------------------------------- | ------------------------ |
| 감지 이벤트 → 일 집계 | `trap_id` + 날짜(KST)            | 이벤트 시각의 날짜       |
| 센서 값 → 일 집계     | `trap_id` + 날짜(KST)            | 일 평균                  |
| 상태 로그 → 작동 시간 | `trap_id` + 날짜(KST)            | `operating` 구간 길이 합 |
| 위치                  | `trap_id` + 날짜 → `location_id` | 위치 이력으로 매핑       |
| 가상 포획 → 일 집계   | `trap_id` + `location_id` + 날짜 | 위 일 집계 행과 1:1      |

### 2-3. 모순 방지 규칙 (반드시 지킴, 테스트로 검증)

1. `sim_captures <= rat_detections` (같은 행 기준)
2. `operating_hours == 0` 이면 `sim_captures == 0`
3. 감지 이벤트 1건은 최대 1번만 포획으로 계산한다 (이벤트 단위 베르누이 시행).
4. 데이터가 부족한 행/위치는 포획을 임의로 채우지 않는다. 집계 단계에서 `is_insufficient` 플래그만 표시한다.
5. 결측 센서 값은 0으로 채우지 않고 `NaN/null` 유지.
6. 포획 관련 컬럼에는 항상 `sim_` 접두사를 붙인다.

## 3. 생성 모델 (가상 데이터 규칙과 가정)

### 3-1. 공통 설정

| 항목      | 값                                                                      |
| --------- | ----------------------------------------------------------------------- |
| 난수      | `numpy.random.default_rng(seed=42)`, 시나리오별로 `seed + 시나리오번호` |
| 분석 기간 | 28일 (D 위치는 3일)                                                     |
| 시간 단위 | 일 집계 행 + 이벤트 단위 감지                                           |
| 출력      | CSV (UTF-8), `data/synthetic/`                                          |

### 3-2. 감지 생성

각 (트랩, 위치, 날짜)에 대해:

1. **쥐 감지 이벤트 수** `~ Poisson(λ_loc × operating_hours × env_factor)`
   - `λ_loc`: 위치별 시간당 쥐 감지율(시나리오 표 참고)
   - `env_factor`: 환경 보정. 온도·습도 각각 최대 ±5%, 합쳐 ±10% 이내의 약한 영향(가정: 따뜻하고 습할수록 활동 증가)
   - 날짜별 날씨 변동(모든 트랩 공통): 온도 `N(0, 2.5℃)`, 습도 `N(0, 6%p)`를 일 단위로 더한다. 별도 시드(`seed+1000`)를 사용한다.
   - 영향이 약해 EDA(127 트랩-일)에서는 온도-감지 상관이 검출되지 않는다(ρ≈-0.05). 환경 영향 검증용이 아니다.
2. **시간대 분포**: 야간(22~05시) 비중 75%, 나머지 25%를 낮에 배분 (가정: 쥐는 야행성)
3. **비대상 동물(non_rat)**: 쥐 감지의 약 15% 추가, **분류 실패(null)**: 전체의 약 5%
4. **분류 신뢰도**: 정상 분류는 0.6~0.99 균등
5. **중복 감지 억제**: 이미 60초 재감지 억제가 적용된 이벤트라고 가정 (API 명세와 동일)

### 3-3. 포획 생성

각 쥐 감지 이벤트마다 독립적으로 포획 여부를 결정한다.

```
p_capture = p_loc × device_factor_trap
sim_captures(일) = Binomial(rat_detections(일), p_capture)
```

- `p_loc`: 위치 특성(쥐가 트랩에 실제로 진입하는 경향)
- `device_factor_trap`: 트랩 장치 상태 계수(1.0=정상, <1 = 문 고장 등으로 포획 저하)
- 가정: 포획된 트랩은 **다음 날 초기화**된다 (하루에 여러 번 포획 가능하다고 단순화).
- 이 가정은 실제 트랩 동작과 다를 수 있으므로 한계 문서에도 기록한다.

### 3-4. 위치와 장치를 구분하기 위한 설계

"감지는 많은데 포획이 낮다"는 원인이 **위치 문제**인지 **장치 문제**인지 알고리즘이 구분할 수 있어야 한다. 구분 단서는 다음과 같이 만든다.

- **위치 문제**: 같은 위치에 어떤 트랩을 두어도 포획률이 낮다.
- **장치 문제**: 같은 트랩을 다른 위치로 옮겨도 포획률이 낮다.

따라서 시나리오에 **트랩 이동 이력**을 포함한다(시나리오 B, F 참고).

### 3-5. 이상 상황 주입

| 이상          | 방식                                                                                      |
| ------------- | ----------------------------------------------------------------------------------------- |
| 작동 중단     | 트랩별로 연속 6~24시간 중단 구간 1~2회. 해당 시간 `operating_hours`에서 제외, 감지·포획 0 |
| 센서 결측     | TVOC/eCO2/온습도 각 2% 무작위 결측 (`null`)                                               |
| 로드셀        | 포획 시에만 값이 생긴다고 가정하지 않고 전부 `null` (실제 데이터 형태가 정해지기 전까지)  |
| 가동 0시간 날 | 전체 중단일 1일 포함 → `operating_hours = 0` 행 검증용                                    |

## 4. 시나리오 정의 (모드 1)

기본 파라미터: `λ_loc`는 쥐 감지율(건/작동시간), `p_loc`는 감지 1건당 포획 확률.

| 위치  | 유형                                | 트랩    | λ_loc | p_loc | device_factor | 기간    | 기대하는 알고리즘 판단                                 |
| ----- | ----------------------------------- | ------- | ----- | ----- | ------------- | ------- | ------------------------------------------------------ |
| LOC-A | 감지·포획 모두 높음                 | TRAP-01 | 0.30  | 0.35  | 1.0           | 28일    | **유지** (좋은 위치)                                   |
| LOC-B | 감지 높음·포획 낮음 (**위치 문제**) | TRAP-02 | 0.30  | 0.05  | 1.0           | 28일    | 재배치 권고 (같은 위치에 있던 TRAP-05도 낮음)          |
| LOC-C | 감지·포획 모두 낮음                 | TRAP-03 | 0.05  | 0.30  | 1.0           | 28일    | 재배치 권고 (감지 자체가 적음)                         |
| LOC-D | **데이터 부족**                     | TRAP-04 | 0.25  | 0.30  | 1.0           | **3일** | **추천 확정 안 함** (`insufficient_data`)              |
| LOC-E | 설치 이력 없는 후보                 | -       | -     | -     | -             | -       | 이력이 없으므로 `new_candidate`, 성과 예측 불확실 표시 |
| LOC-F | 감지 높음·포획 낮음 (**장치 문제**) | TRAP-06 | 0.28  | 0.35  | **0.15**      | 28일    | 위치 문제가 아닌 **장치 점검** 필요로 구분             |

**트랩 이동 이력 (장치/위치 구분용)**

- TRAP-02: LOC-B에서 14일 → LOC-A로 이동 후 14일. LOC-A에서는 성과가 정상이면 → **장치 문제 아님, LOC-B 위치 문제**.
- TRAP-06: LOC-F에서 14일 → LOC-A로 이동 후 14일. LOC-A에서도 포획이 낮으면 → **장치 문제**.
- TRAP-05: LOC-B에서 14일간 운영(B 위치 문제를 다른 트랩으로 재확인).

> 위 숫자는 설계용 초기값이다. 구현 후 요약 통계를 보고 현실성을 점검한 뒤 조정할 수 있으며, 조정하면 이 문서를 함께 수정한다.

## 5. 모드 2 (결합 데이터셋) 생성 규칙

1. 실제 감지 데이터(Pi API)로 `trap_day_summary`를 만든다.
2. 실제 `rat_detections`, `operating_hours`를 그대로 사용한다. 값은 바꾸지 않는다.
3. 포획은 3-3과 같은 방식으로 `sim_captures`만 추가한다. 위치별 `p_loc`는 시나리오 표의 값을 재사용하거나 팀이 별도 지정한다.
4. 모든 행에 `detection_source = "actual"`, `capture_source = "synthetic"`을 기록한다.
5. 실제 감지가 아직 부족한 동안에는 이 모드로 만든 결과를 "알고리즘 성능"으로 보고하지 않는다.

## 6. 데이터 사전

### 6-1. `trap_day_summary` (분석용 통합 데이터셋, 모드 1·2 공통)

| 컬럼                      | 자료형 | 설명                            | 결측 |
| ------------------------- | ------ | ------------------------------- | ---- |
| `trap_id`                 | string | 트랩 ID (`TRAP-01`)             | 불가 |
| `location_id`             | string | 해당 날짜의 설치 위치           | 불가 |
| `date`                    | date   | KST 기준 날짜                   | 불가 |
| `operating_hours`         | float  | 하루 중 실제 작동 시간(h), 0~24 | 불가 |
| `rat_detections`          | int    | 쥐(`rat`) 분류 이벤트 수        | 불가 |
| `non_rat_detections`      | int    | `non_rat` 분류 이벤트 수        | 불가 |
| `unclassified_detections` | int    | 분류 실패(null) 이벤트 수       | 불가 |
| `avg_temperature_c`       | float  | 일 평균 온도                    | 가능 |
| `avg_humidity_pct`        | float  | 일 평균 습도                    | 가능 |
| `avg_tvoc_ppb`            | float  | 일 평균 TVOC                    | 가능 |
| `avg_eco2_ppm`            | float  | 일 평균 eCO2                    | 가능 |
| `sim_captures`            | int    | **가상** 포획 횟수              | 불가 |
| `detection_source`        | string | `actual` / `synthetic`          | 불가 |
| `capture_source`          | string | 항상 `synthetic`                | 불가 |

- `rat_detections`가 0이면 `sim_captures`는 0.
- 평균값 컬럼은 해당 날짜에 유효 측정값이 없으면 `null`.

### 6-2. 파생 지표 (`metrics.py`에서 계산, 저장하지 않아도 됨)

| 지표               | 계산                                    | 비고                            |
| ------------------ | --------------------------------------- | ------------------------------- |
| `detection_rate`   | `rat_detections / operating_hours`      | 작동 시간 대비 감지 빈도        |
| `sim_capture_rate` | `sim_captures / operating_hours`        | **추정 지표**(가상)             |
| `sim_conversion`   | `sim_captures / rat_detections`         | `rat_detections = 0`이면 `null` |
| `non_rat_ratio`    | `non_rat / (rat + non_rat)`             | 정답 라벨이 있을 때만 의미 있음 |
| `is_insufficient`  | 관측 일수 < 7일 또는 작동 시간 합 < 72h | 임계값은 EDA 후 확정            |

### 6-3. `detection_events` (모드 1에서 생성, 실제 API 스키마와 동일)

API 명세 2-6과 같은 컬럼: `event_id`, `trap_id`, `detected_at`, `ir_detected`, `classification`, `confidence`. 모드 1에서는 추가로 `data_source = "synthetic"` 컬럼을 붙인다.

### 6-4. `simulated_captures` (이벤트 단위 가상 포획 로그, 선택)

| 컬럼             | 자료형   | 설명                                   |
| ---------------- | -------- | -------------------------------------- |
| `sim_capture_id` | int      | 고유 ID                                |
| `event_id`       | int      | 연결된 감지 이벤트 (이벤트당 최대 1건) |
| `trap_id`        | string   |                                        |
| `location_id`    | string   |                                        |
| `captured_at`    | datetime | 이벤트 시각 이후                       |
| `data_source`    | string   | 항상 `synthetic`                       |

일 집계의 `sim_captures`는 이 로그를 날짜별로 센 값과 같아야 한다.

## 8. 검증 계획 (구현 후 pytest)

- 시드 고정 시 같은 파일이 생성된다.
- 2-3의 모순 방지 규칙 1~3, 5를 모든 행에서 검사한다.
- 일 집계의 `sim_captures` 합 = `simulated_captures` 건수.
- 위치별 평균 포획 전환율이 설계값(`p_loc`)에 근접한다(허용 오차 내).
- 시나리오 D는 관측 일수가 3일이며 `is_insufficient = True`.

## 9. 한계 및 주의

- 시나리오의 `λ_loc`, `p_loc`는 **현장 데이터에서 추정한 값이 아니라 설계자가 정한 가정**이다.
- 이 데이터로 얻은 알고리즘 정확도는 "가상 환경에서 설계 의도를 구분하는 능력"일 뿐이며, 실제 현장 성능이 아니다.
- 알고리즘이 가상 데이터를 만든 규칙(포아송·이항 가정)에 맞게 과적합될 수 있다. 이를 피하기 위해 알고리즘은 단순 규칙·점수 기반으로 두고, 생성 모델의 파라미터를 직접 쓰지 않는다.
- 하루 단위 집계로 시간대 효과(야행성)는 이벤트 로그에서만 볼 수 있다.

## 10. 확인이 필요한 결정 사항

1. 시나리오 구성(A~F, 트랩 이동 이력 포함)이 충분한지
2. 분석 기간 28일, 데이터 부족 기준(7일 / 72시간)
3. "포획된 트랩은 다음 날 초기화" 가정
